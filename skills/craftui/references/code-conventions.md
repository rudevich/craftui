# Как писать код

Принципы — по мотивам [Ponytail](https://github.com/dietrichgebert/ponytail) (MIT): решить задачу целиком, написав как можно меньше нового кода.

## Перед тем как писать

- Прочитай то, что уже есть: `src/components/*` (особенно соседние и вложенные компоненты), `src/tokens.css`, `src/lib/`.
- Перечисли все места, которых касается изменение: экспорты (`npm run gen`), демо, тесты, компоненты-потребители (найди их поиском по `from '../<Name>'`).
- Подумай, что изменение может сломать у потребителей: API, классы, токены.

## Лестница решений — первая ступень, которая полностью работает

1. **Это нужно вообще?** Никаких пропсов, вариантов, опций и анимаций, которых нет в макете или не просил пользователь. Пропущенное — одной строкой в отчёте.
2. **Уже есть в проекте?** Соседний компонент, токен, `cx` из `src/lib/cx.ts`.
3. **Платформа?** `<button>`, нативный `disabled`, `<label>`, CSS `:hover`, `:focus-visible`, `:disabled`, `:has()` вместо JS-состояний.
4. **Уже установленная зависимость?** Новые зависимости ради пары строк не добавляются.
5. **Одна понятная строка?** Пиши её.
6. Иначе — минимальный код, который работает.

## Правила

- Без абстракций, обёрток, HOC, конфигов, фабрик и кода «на будущее».
- `hooks.ts`, `utils.ts`, `constants.ts` создавай, только когда есть что в них положить.
- Значения храни в том виде, в каком их даёт платформа. Удалить лучше, чем добавить. Структуру и соглашения проекта не меняй.
- Комментарии объясняют только «почему» — одной строкой.
- При правке общего (токен, вложенный компонент) сначала найди всех потребителей и исправь причину один раз, в общем месте.
- Из двух решений одного размера выбирай то, которое правильно обрабатывает крайние случаи.
- Нетривиальная логика (ветвления, обработчики, хуки) получает хотя бы один rstest. Код без проверки не закончен.
- Сознательный компромисс помечай комментарием `shortcut: <ограничение>, <когда пересмотреть>`, например `/* shortcut: тень приближена одной box-shadow, пересмотреть при второй тени в макете */`. `npm run craftui -- shortcuts` соберёт такие комментарии в лог.

## Никогда не урезать

- Доступность: семантичные теги, `aria-*` там, где их нет у тега, видимый фокус (`:focus-visible`), клавиатура, `alt` и `aria-hidden` у графики.
- Обработку ошибок и то, что явно попросил пользователь.

## React 19 + TypeScript

- Функциональные компоненты: `export function Button(props: ButtonProps)`. Default-экспорт не используй.
- `ref` — обычный проп (входит в `ComponentPropsWithRef<'button'>`), `forwardRef` не нужен.
- Импорт React не нужен (automatic JSX runtime), типы импортируй через `import type`.
- Пропсы — в `types.ts`, `Omit<ComponentPropsWithRef<'tag'>, …> & { … }`, JSDoc одной строкой со ссылкой на свойство Figma.
- Значения по умолчанию — в деструктуризации: параметров или `const { … } = props` первой строкой тела (README берёт их оттуда).
- Поле ввода (`<input>` внутри рамки): пропсы от `ComponentPropsWithRef<'input'>`, `ref` и нативные атрибуты — на input, `className` и `style` — на корень. Напиши это JSDoc-ом над `export type <Name>Props`: README выводит его вместо «атрибуты передаются корневому элементу».
- Сочетания, которых нет в макете, запрещай типом: `{ outline?: false; view?: View } | { outline: true; view?: OutlineView }`. JSDoc повторяй в обеих ветках union, иначе docgen его теряет и README останется без описания.
- `<button>` по умолчанию `type="button"`, чтобы не отправлять форму.

## CSS Modules

- Имена классов — camelCase по смыслу (`root`, `label`, `icon`), не по слоям вида `frame123`. Классы должны совпадать с `craftlog/figma/node-map.json` (style-check ищет элементы по ним).
- Варианты — `[data-size='m']`, состояния — псевдоклассы. `!important` и глобальные селекторы не используются.
- Значения — `var(--token)` из `src/tokens.css`. Сырые значения допустимы, только когда токена нет (они видны в `css` узла spec).
- **Единицы: размеры только в `px` или `%`.** Запрещены `em`, `rem`, `ch`, `ex`, `pt`, `cm` и т. п. — и в CSS, и в inline-стилях. Безразмерные множители (`line-height: 1.2`, `opacity`, `flex: 1`) и `fr` в сетках — не размеры, их можно.
- Viewport-единицы (`vw`, `vh`, `dvh`, `svh`, `lvh`, `vmin`, `vmax`) — только у оверлеев, привязанных к экрану (модальное окно, попап, шторка), и с комментарием-обоснованием в том же правиле: `.overlay { /* units: модальное окно на всю высоту экрана */ max-height: 100dvh; }`.
- `craftui verify` и `npm run craftui -- units <Name>` проверяют это и показывают `файл:строка`. Без обоснования viewport-единица считается ошибкой.
- Шрифты подключаются в `demo/fonts.ts` (только для демо и тестов). Библиотека задаёт `font-family`, а сами шрифты подключает потребитель.
